# Tags for bb-plugin-todo — design spec

Date: 2026-08-26
Status: implemented

This document is the design record for the tags feature. Where it
disagrees with `contract.ts` after implementation, `contract.ts` wins and
this document must be corrected.

---

## 0. Decisions already made (do not relitigate)

| Question | Decision |
|---|---|
| Management surface | **Hybrid** — inline picker applies + creates; a `Manage tags…` dialog does rename/recolor/delete/reorder |
| Tag scope | **Global** across all lists/tabs. `tags` has no `list_id` |
| Filter the board by tag | **No.** Display only, for now. Schema must not preclude adding it later |
| Chip rendering | Colored dot + name at `md` and up; **bare dots with tooltips below `md`** |
| Picker trigger | A **dedicated, always-visible 🏷 icon** on every row, between calendar and plus |
| Subtasks | **Can carry tags**, same as top-level rows |

Explicit non-goals: filtering, tag groups/hierarchy, per-list tag scoping,
custom hex colors, bulk tag operations, tag-based sorting.

---

## 1. Data model

### 1.1 Entities

```
Tag      id, name, color, sortOrder, createdAt
TaskTag  (taskId, tagId)          -- pure join, no payload
```

### 1.2 Color is a palette key, never a hex

Store `"violet"`, not `"#8b5cf6"`. The plugin is themed with shadcn tokens and
renders in both light and dark mode; a stored hex is guaranteed to be
unreadable in one of them. The key is resolved to Tailwind utility classes on
the client (`lib/tag-colors.ts`).

The eight keys, in palette order:

```
slate  red  amber  green  teal  blue  violet  pink
```

`color` is validated against this list at the contract boundary
(`z.enum(TAG_COLORS)`). An unknown key is an `invalid_input` error, not a
silent fallback.

### 1.3 Invariants

1. Tag names are unique **case-insensitively**. `createTag("Urgent")` when
   `urgent` exists throws `invalid_input: a tag named "urgent" already exists`.
   Same rule applies to `updateTag` renames (renaming a tag to its own current
   name, in any casing, is allowed and is a no-op on the uniqueness check).
2. Tag names are trimmed. An empty-after-trim name throws
   `invalid_input: name must not be empty`.
3. Deleting a tag cascades its `task_tags` rows. Tasks survive untouched.
4. Deleting a task cascades its `task_tags` rows. Tags survive untouched.
5. No cap on tags per task. The row UI degrades gracefully (§3.2).
6. `TaskDto.tags` is always ordered by `tags.sort_order`, never by insertion
   order — so chip order is consistent across every row on the board.

## 2. Storage

### 2.1 Migrations — APPEND ONLY

`MIGRATIONS` in `lib/db.ts` currently ships indices 0–5. **Never edit,
reorder, or delete a shipped statement.** Append exactly these four, in this
order, as indices 6, 7, 8, 9:

```sql
-- 6
CREATE TABLE IF NOT EXISTS tags (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  color      TEXT NOT NULL,
  sort_order REAL NOT NULL,
  created_at INTEGER NOT NULL
);

-- 7
CREATE UNIQUE INDEX IF NOT EXISTS tags_name_unique ON tags (name COLLATE NOCASE);

-- 8
CREATE TABLE IF NOT EXISTS task_tags (
  task_id TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  tag_id  TEXT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (task_id, tag_id)
);

-- 9
CREATE INDEX IF NOT EXISTS task_tags_tag_idx ON task_tags (tag_id);
```

`server.ts` already runs `conn.pragma("foreign_keys = ON")`, so both
`ON DELETE CASCADE` clauses are live. Do not add a second pragma call.

Migration 7 makes the uniqueness invariant a database constraint as well as
an application check. The application check exists to produce a readable
error message; the index exists so a race can't defeat it.

### 2.2 IDs

Add to `lib/ids.ts`, following the existing pattern exactly:

```ts
export function mintTagId(): string {
  return mint("tag_");
}
```

### 2.3 Ordering

`tags.sort_order` reuses the existing fractional-ordering scheme.
`createTag` appends: `MAX(sort_order) + 1000`, mirroring `createList`.
`reorderTags` renumbers to `1000, 2000, …`, mirroring `reorderLists`.
No new ordering logic, no changes to `lib/order.ts`.

### 2.4 The N+1 trap — read this before touching `getBoard`

`getBoard` builds its DTO tree through `buildTopLevelDto` → `taskRowToDto`,
once per row. Looking up tags inside `taskRowToDto` means one query per task
per board load. **Do not do that.**

Instead, materialize the whole join once per read call:

```ts
type TagMap = Map<string, TagRefDto[]>;

/** One query. Every task's tags, ordered by tag sort_order. */
function loadTagMap(db: Database.Database): TagMap {
  const rows = db.prepare(`
    SELECT tt.task_id, t.id, t.name, t.color
    FROM task_tags tt
    JOIN tags t ON t.id = tt.tag_id
    ORDER BY t.sort_order
  `).all() as { task_id: string; id: string; name: string; color: TagColor }[];
  const map: TagMap = new Map();
  for (const r of rows) {
    const list = map.get(r.task_id);
    const ref = { id: r.id, name: r.name, color: r.color };
    if (list) list.push(ref);
    else map.set(r.task_id, [ref]);
  }
  return map;
}
```

Threading: `taskRowToDto` gains a fourth parameter `tags: TagRefDto[]`.
`buildTopLevelDto` and `getArchive`'s `dtoFor` gain a `tagMap: TagMap`
parameter and read `tagMap.get(row.id) ?? []`. `getBoard` and `getArchive`
each call `loadTagMap` **once**, at the top.

For the single-DTO returns (`createTask`, `updateTask`, `setTaskTags`), a
targeted per-task query is correct and cheap — add a
`getTaskTags(db, taskId): TagRefDto[]` helper for those. Do not use
`loadTagMap` there.

### 2.5 Existing databases

No backfill. `tags` starts empty, every existing task resolves to `tags: []`,
nothing regresses. There is no data migration step.

## 3. Contract

### 3.1 New types in `contract.ts`

```ts
export const TAG_COLORS = [
  "slate", "red", "amber", "green", "teal", "blue", "violet", "pink",
] as const;
export type TagColor = (typeof TAG_COLORS)[number];

/** The denormalized form embedded in every TaskDto. */
export interface TagRefDto {
  id: string;
  name: string;
  color: TagColor;
}

/** The catalog form, returned by getBoard and the tag mutations. */
export interface TagDto extends TagRefDto {
  sortOrder: number;
  /** Global count across all lists. */
  taskCount: number;
}
```

`TaskDto` gains exactly one field:

```ts
  /** Ordered by tag sortOrder. Populated on subtasks too. */
  tags: TagRefDto[];
```

`getBoard`'s output gains exactly one field:

```ts
  /** The full tag catalog with usage counts, so the picker needs no extra fetch. */
  tags: TagDto[];
```

Both zod objects are `.strict()`. Adding a field to a strict object is safe
here because server and app ship together in one bundle.

`getArchive`'s output is **not** extended with the catalog — archived rows
carry `TaskDto.tags` like any other row, but the archive panel does not
render a picker, so it needs no catalog.

### 3.2 New RPC methods

Exactly five. No more, no fewer.

```ts
createTag: {
  input:  z.object({ name: z.string(), color: z.enum(TAG_COLORS) }).strict(),
  output: z.object({ tag: tagDtoSchema }).strict(),
},
updateTag: {
  input:  z.object({
    id: idSchema,
    name: z.string().optional(),
    color: z.enum(TAG_COLORS).optional(),
  }).strict(),
  output: z.object({ tag: tagDtoSchema }).strict(),
},
deleteTag: {
  input:  z.object({ id: idSchema }).strict(),
  output: z.object({ ok: z.literal(true) }).strict(),
},
reorderTags: {
  input:  z.object({ ids: z.array(idSchema) }).strict(),
  output: z.object({ tags: z.array(tagDtoSchema) }).strict(),
},
setTaskTags: {
  input:  z.object({ taskId: idSchema, tagIds: z.array(idSchema) }).strict(),
  output: z.object({ task: taskDtoSchema }).strict(),
},
```

**`setTaskTags` is a full-set replace, not add/remove pairs.** The picker
always holds the complete selection for a task, so replace is the natural
shape, and it is idempotent — a double-click or a retried request cannot
corrupt state. Implementation: inside one transaction,
`DELETE FROM task_tags WHERE task_id = ?` then insert each id. Unknown tag
ids throw `invalid_input: tag not found`; duplicate ids in the input array are
deduped, not an error.

### 3.3 `server.ts` wiring

Thin, matching the existing style. Every tag mutation publishes on the
`"board"` realtime channel so open panels refetch:

```ts
createTag(input)  { const tag = db.createTag(conn, input, new Date());  publish(null); return { tag }; }
```

`publish(null)` (rather than a specific list id) is correct for tag
mutations: tags are global, so every list's board is potentially affected.
`setTaskTags` publishes the affected task's `listId`.

## 4. UX

### 4.1 Row at rest

Chips sit immediately after the title, before the progress ring. The 🏷 icon
slots between the calendar and the plus.

```
┌───────────────────────────────────────────────────────────────────────────┐
│  BACKLOG · 12                                        ◔ 3/12 overdue       │
│ ┌───────────────────────────────────────────────────────────────────────┐ │
│ │ ⠿ ☐  Rewrite onboarding email ●urgent ●bug     2mo  2d late  ▤ 🏷 ＋ ⋯ │ │
│ │ ⠿ ☐  Renew the domain                          3d   in 3d    ▤ 🏷 ＋ ⋯ │ │
│ │ ⠿ ☐  Q3 planning doc  ●deep-work  ◕2/5         1w   Fri 9am  ▤ 🏷 ＋ ⋯ │ │
│ │     ↳ ☐ Pull last quarter's numbers ●waiting   1w             ▤ 🏷   ⋯ │ │
│ │ + add to backlog                                                      │ │
│ └───────────────────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────────────────┘
```

Subtask rows show chips and the 🏷 icon; they still never show the ＋ icon
(depth is capped at 1 — unchanged).

### 4.2 Responsive collapse and overflow

Mirrors the `hidden sm:inline-flex` trick `AgeChip` already uses — two
sibling elements, one visible per breakpoint, not JS measurement.

```
  ≥ md    ●urgent ●bug ●deep-work       full chips: dot + name
  < md    ● ● ●                         bare dots, name in tooltip
  > 3     ●urgent ●bug ●qa  +2          overflow counter; tooltip lists the rest
```

The overflow cap is 3 chips at `md`+ and 5 dots below `md`.

### 4.3 The 🏷 picker (Popover)

```
   idle                              typing a new name
 ┌─ Tags ───────────────────┐      ┌─ Tags ───────────────────┐
 │ ⌕ filter or create…      │      │ ⌕ design▮                │
 ├──────────────────────────┤      ├──────────────────────────┤
 │ ☑ ● urgent            12 │      │ ＋ Create "design"   ● ▾ │◄─ swatch
 │ ☑ ● bug                8 │      ├──────────────────────────┤
 │ ☐ ● deep-work          3 │      │ ☐ ● design-review      2 │
 │ ☐ ● waiting            1 │      └──────────────────────────┘
 ├──────────────────────────┤
 │ ⚙ Manage tags…           │
 └──────────────────────────┘

   empty state                        the swatch popover
 ┌─ Tags ───────────────────┐      ┌─ pick a colour ────────┐
 │ ⌕ filter or create…      │      │  ● ● ● ●               │
 ├──────────────────────────┤      │  ● ● ● ●               │
 │  No tags yet.            │      │ slate red amber green  │
 │  Type a name to create   │      │ teal blue violet pink  │
 │  your first one.         │      └────────────────────────┘
 └──────────────────────────┘
```

Behaviour:

- The search input filters the list case-insensitively.
- The `＋ Create "…"` row appears only when the trimmed query is non-empty
  **and** does not exactly match an existing tag name (case-insensitive).
- The create row's swatch defaults to the next unused palette color, cycling
  by `tags.length % 8` — so the first eight tags are all visually distinct
  without the user choosing anything.
- Creating a tag also **immediately applies it** to the current task, and
  clears the query.
- Toggling a checkbox fires `setTaskTags` with the new full set. The popover
  **stays open** so several tags can be applied in one pass.
- Toggles are optimistic: the chip appears on the row before the RPC lands,
  and reverts with a toast on failure.
- `Esc` closes. `Enter` in the query field commits the create row if it is
  showing, otherwise toggles the first filtered result.
- Counts on the right are `TagDto.taskCount` — global, not per-list.

### 4.4 `⚙ Manage tags…` → the tag manager

Rendered through the existing `components/ui/responsive-overlay.tsx` —
centred Dialog on desktop, bottom drawer on compact — exactly as
`ArchivePanel` does. Do not hand-roll a dialog.

```
┌── Manage tags ──────────────────────────────── [ + New tag ] ──┐
│                                                                 │
│  ⠿   ● ▾   urgent                    12 tasks              🗑   │
│  ⠿   ● ▾   bug                        8 tasks              🗑   │
│  ⠿   ● ▾   deep-work                  3 tasks              🗑   │
│  ⠿   ● ▾   waiting                    1 task               🗑   │
│  ⠿   ● ▾   ▮design                    0 tasks              🗑   │  ← new, focused
│                                                                 │
│  drag ⠿ to reorder · order drives chip order on every row      │
└─────────────────────────────────────────────────────────────────┘

  empty state:  "No tags yet. Create one to start labelling tasks."
                with the [ + New tag ] button as the only affordance.
```

- Click the name → inline rename, `Enter` commits, `Esc` reverts. Same
  pattern and same keyboard contract as `TabStrip`'s rename.
- Click `● ▾` → the eight-swatch popover from §4.3.
- Drag `⠿` → reorder, committed via `reorderTags`. Uses its **own**
  `DndContext` local to the dialog — do **not** try to reuse `TodoPage`'s
  board-level context; the dialog is a portal and the sensors would fight.
- Click `🗑` → `AlertDialog` confirm, worded with the live count:

```
        ┌────────────────────────────────────────┐
        │  Delete "urgent"?                      │
        │  It will be removed from 12 tasks.     │
        │  This cannot be undone.                │
        │              [ Cancel ]  [ Delete ]    │
        └────────────────────────────────────────┘
```

  When `taskCount` is 0 the second line reads "This cannot be undone." alone.

### 4.5 Mounting the manager

`TagManagerDialog` mounts **once**, in `TodoPage`. It is opened by a new
`board-bus` command, not by prop-drilling through every row:

```ts
export type BoardCommand = "open-archive" | "create-list" | "open-tag-manager";
```

If it were mounted inside `TagPicker`, a twenty-row board would mount twenty
dialogs. Mount once, emit to open.

### 4.6 Density

Four muted icons × ten rows is the real cost of the always-visible 🏷. The
mitigation is the existing convention, not a new mechanism: all four icon
buttons sit at `text-muted-foreground` at rest and only the hovered or
keyboard-focused one lifts to `text-foreground`. Rows stay `min-h-8`; the
🏷 button is `size-6` with a `size-4` glyph, identical to its neighbours.

## 5. Frontend modules

### 5.1 `lib/tag-colors.ts`

**The single most likely way to break this feature is Tailwind JIT.**
Class names must appear as complete literal strings in the source. A
template-interpolated `` `bg-${color}-500` `` is invisible to the scanner and
every chip renders colorless. Use static records:

```ts
import type { TagColor } from "@/contract";

/** Dot fill. Literal strings — never interpolate, JIT would strip them. */
export const TAG_DOT_CLASS: Record<TagColor, string> = {
  slate:  "bg-slate-500",
  red:    "bg-red-500",
  amber:  "bg-amber-500",
  green:  "bg-green-500",
  teal:   "bg-teal-500",
  blue:   "bg-blue-500",
  violet: "bg-violet-500",
  pink:   "bg-pink-500",
};

/** Chip text + subtle background, tuned for light and dark. */
export const TAG_CHIP_CLASS: Record<TagColor, string> = {
  slate:  "text-slate-700  dark:text-slate-300  bg-slate-500/10",
  /* …one literal entry per key… */
};

/** Ring shown on the selected swatch in the color picker. */
export const TAG_RING_CLASS: Record<TagColor, string> = { /* … */ };

/** Human label under each swatch. */
export const TAG_COLOR_LABEL: Record<TagColor, string> = { slate: "Slate", /* … */ };
```

### 5.2 Component inventory

| File | Responsibility | Notes |
|---|---|---|
| `components/TagChip.tsx` | One tag: dot + name, or dot only | `compact?: boolean`; dot-only renders a `Tooltip` with the name |
| `components/TagChips.tsx` | A row's tag list | Breakpoint pair + overflow `+N`; renders nothing for `[]` |
| `components/ColorSwatchPicker.tsx` | The 8-swatch grid | Controlled: `value`, `onChange`; used by both picker and manager |
| `components/TagPicker.tsx` | The 🏷 Popover (§4.3) | Owns query state; calls `setTaskTags` / `createTag` |
| `components/TagManagerDialog.tsx` | The manager (§4.4) | `responsive-overlay`; own `DndContext` |

### 5.3 Icon

`components/ui/icon.tsx` has no tag glyph. Add one mapping, alphabetically
placed with its neighbours, importing from the already-installed
`@hugeicons/core-free-icons`:

```ts
Tag: Tag01Icon,
```

(`Tag01Icon`, `Tag02Icon`, `TagIcon`, and `TagsIcon` all exist in the
installed package. Use `Tag01Icon`.)

## 6. Testing

The repo tests with vitest (`npm test`) and typechecks with `tsc --noEmit`
(`npm run typecheck`). Both must pass clean.

**`lib/db.test.ts`** — new `describe("tags")`:
- create → appears in `listTags` with `sortOrder` after existing tags
- duplicate name, differing only in case, throws
- empty / whitespace-only name throws
- rename to a colliding name throws; rename to own name in new casing succeeds
- `deleteTag` removes assignments but leaves tasks intact
- `deleteTask` removes assignments but leaves tags intact
- `setTaskTags` replaces the full set; is idempotent; dedupes duplicate input
  ids; throws on an unknown tag id
- `getBoard` returns `tags: []` for untagged tasks, ordered refs for tagged
  ones, and populates tags on **subtasks**
- `reorderTags` renumbers and the new order is reflected in `TaskDto.tags`

**`server.test.ts`** — each of the five methods round-trips through the
registered contract and rejects a malformed input (bad color key, unknown id).

**`components/leaf.test.tsx`** — `TagChip` renders name at full width and
tooltip-only when `compact`; `TagChips` renders `+N` past the cap; renders
null for an empty array; `ColorSwatchPicker` marks the selected swatch and
fires `onChange`.

**`components/TodoPage.test.tsx`** — picker opens from the row 🏷, toggling a
checkbox calls `setTaskTags` with the correct full set, the create row appears
only for a non-matching query, and `Manage tags…` emits `open-tag-manager`.
