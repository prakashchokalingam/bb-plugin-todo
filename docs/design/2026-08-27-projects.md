# Projects in the Backlog — design

Status: approved 2026-08-27
Date: 2026-08-27

## Problem

The board has two zones and one flat list inside each. A day's Today list ends
up holding a dozen rows that are really "the third subtask of the onboarding
rewrite" and "step two of Q3 planning" — but by the time they land in Today
they have no parent, no grouping, and no way to tell which effort they belong
to.

The cause is mechanical, not cosmetic. The relationship is not hidden by the
renderer; it is deleted on drop. No amount of UI work can render a trail that
nothing stores.

**Corrected during Phase 1-3 (2026-08-27).** An earlier draft of this document
blamed `lib/db.ts:586`. That line is the promoted-children re-parenting block
and is unrelated. The DB layer has always taken `parent_id` from the caller
verbatim. The real offender is **`lib/drag.ts:106`**, which sends
`parentId: null` on every cross-bucket drop — so the loss is client-side, and
the central fix lands in **Phase 4**, not Phase 2. Phase 2 still removes a
genuine second offender: the cascade that forced a parent's children to follow
its bucket/day (old lib/db.ts ~562-571).

## Naming

The entity is called **Project** in code, DB, and UI — not "Section".
`components/Section.tsx` already means "the Backlog zone / the Today zone",
and reusing the word would make every prop name ambiguous.

```
List (tab)  ->  Project  ->  Task  ->  Subtask
Work            Q3 Launch    Rewrite email   Get legal sign-off
```

Task depth stays capped at one level. A Project is a container, not a task, so
this buys a third level of context without a third level of nesting.

## Core decision

**Today stops being a place and becomes a flag.**

A task's home is `(project_id, parent_id)` and it never leaves. Dragging into
Today sets `bucket='today'` + `day` and nothing else about its identity. The
task renders in Today with its trail, and stays visible — ghosted — in its
project. This is the Todoist / Things / Linear model.

`bucket` keeps its column name (append-only migration convention) but changes
meaning: `'today'` now reads "scheduled for `day`", not "lives in the Today
list".

## Data plan

### New entity: Project

```
id           TEXT PRIMARY KEY
list_id      TEXT NOT NULL REFERENCES lists(id) ON DELETE CASCADE
name         TEXT NOT NULL
color        TEXT NOT NULL      -- reuses TAG_COLORS from contract.ts
collapsed    INTEGER NOT NULL DEFAULT 0
sort_order   REAL NOT NULL
created_at   INTEGER NOT NULL
```

`color` reuses the existing eight-key palette and `lib/tag-colors.ts`
resolution, so a project badge is readable in both themes with no new colour
code. It is not decoration: the trail line in Today must be scannable across
ten rows, and a colour does that faster than a name.

`collapsed` is server-side. Single-user local plugin; persisting it across
reloads is worth one column and costs nothing.

### Changes to Task

```
+ project_id  TEXT REFERENCES projects(id)   -- NULL = loose
+ today_order REAL                            -- NULL iff bucket='backlog'
```

`sort_order` now means *position within its project (or the loose group),
under its parent*. `today_order` means *position in the Today list*. A task
that is both filed and scheduled needs both; without the split, reordering the
day silently reshuffles the Backlog.

`parent_id` is no longer cleared on a cross-bucket move. That single change is
what makes the trail possible.

### Derived, denormalized onto TaskDto

```ts
trail: {
  projectId: string | null
  projectName: string | null
  projectColor: TagColor | null
  parentId: string | null
  parentTitle: string | null
} | null
```

Computed server-side in the same pass that already denormalizes tags, so the
client never does a lookup to render a row. `null` for a loose top-level task —
those rows render exactly as they do today.

### Invariants (each gets a test)

1. Depth cap: a task with `parent_id != NULL` can never be a parent.
2. A subtask's `project_id` always mirrors its parent's. Enforced inside the
   move/create transaction, not by convention.
3. A task's project must belong to the task's list.
4. Scheduling a subtask does not schedule its parent, and scheduling a parent
   does not drag its subtasks along (reverses lib/db.ts:565).
5. `today_order IS NULL` iff `bucket = 'backlog'`.
6. Deleting a project releases its tasks to loose. It never cascades into the
   bin.

## Storage plan

Appended to `MIGRATIONS` (never edit or reorder a shipped statement):

```
10  CREATE TABLE projects (...)
11  CREATE INDEX projects_list_idx ON projects (list_id, sort_order)
12  ALTER TABLE tasks ADD COLUMN project_id TEXT REFERENCES projects(id)
13  ALTER TABLE tasks ADD COLUMN today_order REAL
14  CREATE INDEX tasks_project_idx ON tasks (list_id, project_id, sort_order)
15  UPDATE tasks SET today_order = sort_order WHERE bucket = 'today'
```

Migration 15 is the backfill: every existing Today row keeps its exact current
position on first load.

**Backward compatibility is total.** Every existing task gets
`project_id = NULL` and renders as a loose row below the projects —
pixel-identical to today's board. Nothing about the plugin looks different
until the user creates their first project.

**Verify before relying on it:** `PRAGMA foreign_keys` may be off in this DB.
Project deletion therefore releases tasks explicitly inside the transaction
rather than trusting `ON DELETE SET NULL`. Confirm the pragma state in Phase 1
and note it in the test.

### Query changes

`getBoard`'s backlog query (lib/db.ts:335) currently filters
`bucket = 'backlog'`. It must now also return today-flagged rows so the ghost
renders in its project. The Today query (lib/db.ts:328) is unchanged apart
from ordering by `today_order`.

`runRollover` is **untouched**. Its predicate — `status='open' AND
bucket='today' AND day < today` — never cared that bucket was a location.
Carry counting works identically, and now a `carried 6x` badge sits on a row
that still knows which project it is stalling.

Changed:

```
moveTask   input  + projectId: id | null   (target home; omit = unchanged)
createTask input  + projectId: id | null
getBoard   output + projects: ProjectDto[]
                  + backlog.tasks now includes today-flagged ghosts

```

```ts

  id, listId, name, color, sortOrder, collapsed,
  openCount, todayCount, overdueCount
```

## UX

### Board

```
+--------------------------------------------------------------------------------------+
|  Work | Personal | +                                                 (2) overdue      |
+--------------------------------------------------------------------------------------+
|  BACKLOG . 12                                                    (o) 3/12 overdue     |
|  +--------------------------------------------------------------------------------+  |
|  | v # Q3 Launch                                  4 open . 1 today       + ...     |  |
|  |   :: [ ] Rewrite the onboarding email  *urgent  (o)1/3   2d late  [] # + ...    |  |
|  |         -> [ ] Draft the copy                                     [] #   ...    |  |
|  |         -> (.) Get legal sign-off      . today                    [] #   ...    |  |
|  |   :: [ ] Q3 planning doc  *deep-work  (o)2/5           Fri 9:00am [] # + ...    |  |
|  |   + add to Q3 Launch                                                            |  |
|  |                                                                                 |  |
|  | > # Personal errands                           3 open                 + ...     |  |
|  |                                                                                 |  |
|  |   :: [ ] Renew the domain                              in 3 days  [] # + ...    |  |
|  |   + add to backlog                                       ^opt new project #     |  |
|  +--------------------------------------------------------------------------------+  |
|                                                                                       |
|  TODAY . Thu 27 Aug                                              (o) 5/10 done        |
|  +--------------------------------------------------------------------------------+  |
|  | :: [ ] Get legal sign-off                            carried 1x   [] #   ...    |  |
|  |      # Q3 Launch > Rewrite the onboarding email                                 |  |
|  | :: [ ] Ship the invoice fix                          in 22 min    [] # + ...    |  |
|  | :: [ ] Draft the copy                                             [] #   ...    |  |
|  |      # Q3 Launch > Rewrite the onboarding email                                 |  |
|  | + add to today                                                                  |  |
|  +--------------------------------------------------------------------------------+  |
+--------------------------------------------------------------------------------------+
```

Legend: `v`/`>` collapse chevron, `#` project badge (colour dot + name), `(.)`
ghost checkbox, `::` drag handle, `->` subtask.

### Trail line

Second line, muted, `# Project > Parent`. Rules:

- Renders only when there is context to show. A loose top-level task gets no
  second line, so rows never gain height for nothing.
- Truncates from the **left** — `# Q3 Launch > ...boarding email` — so the
  nearest ancestor, the most useful segment, survives.
- Each segment is clickable: scrolls the Backlog to the source row and flashes
  it.
- Below `md`, collapses to the project badge alone (`# Q3 Launch`), matching
  how TagChips already degrades.

### Ghost row

A scheduled task stays in its project, dimmed, checkbox replaced by `(.)`,
with a `. today` marker. Once `carried >= 3` the ghost also shows the carry
count:

```
|   :: [ ] Rewrite the onboarding email  (o)1/3    2d late   [] # + ...  |
|         -> (.) Get legal sign-off      . today ~6          [] #   ...  |
```

This is the point of the feature beyond breadcrumbs: avoidance becomes visible
next to the project it is stalling, not only in a day view you scroll past.
Clicking the ghost's marker unschedules it.

### Project header

```
| v # Q3 Launch                                4 open . 1 today    + ... |
```

- chevron toggles collapse (persisted via setProjectCollapsed)
- badge colour opens the same `ColorSwatchPicker` tags already use
- name is inline-editable, like tab rename
- `+` reveals the add-task input filed to this project
- `...` -> Rename / Change colour / Delete project

Delete confirm, reusing the existing AlertDialog:

```
+-- Delete "Q3 Launch"? --------------------------+
|  4 tasks will move to the Backlog, unfiled.     |
|  Nothing is deleted.                            |
|                          [Cancel]  [Delete]     |
+-------------------------------------------------+
```

### Creating a project

Two entry points, no dialog:

1. The Backlog add-row gains a trailing affordance — `^opt new project #` —
   and typing `#Name` then Enter creates the project inline.
2. Dragging one task onto another *within the Backlog*, held for 600ms, offers
   "group into new project", pre-named from the target's title.

Entry point 1 ships in this change. Entry point 2 is deferred.

### Loose tasks

Unfiled tasks render **below** all projects, in the same Backlog card, with no
group header. This is the migration path for every existing task.

### Drag matrix

```
from            to                        result
----            --                        ------
project task    Today                     flag scheduled; ghost stays
subtask         Today                     flag scheduled; parent_id KEPT
Today row       Backlog (anywhere)        unschedule; snaps home to its slot
Today row       another project's header  unschedule AND re-home
Today row       Today                     reorder (writes today_order only)
project task    another project           re-home (writes sort_order only)
project task    loose area                project_id = NULL
loose task      project body              file into project
project header  project header            reorder projects
```

The snap-home rule matters: dropping a Today row into the Backlog does not
leave it where the pointer was. It returns to its own project slot, because
that is where it has been living the whole time. Only a drop directly on a
*different* project header re-homes it.

### Empty states

```
| v # Q3 Launch                                       0 open      + ... |
|   + add to Q3 Launch                                                  |
```

An empty project shows only its add-row. Projects are never auto-deleted; an
empty one is a plan you have not written yet.

## Flow

### Daily flow

1. Work accumulates in the Backlog, filed into projects, broken into subtasks.
   This is the thinking surface.
2. Each morning you drag a handful of leaves into Today. Each one keeps its
   trail. Today is a commitment list, not a copy of your plans.
3. Anything unfinished carries at midnight — same rollover, same badge — but
   the badge now sits next to the project name, so a stalled effort is legible
   as a stalled *effort*.
4. Completing marks it done everywhere: leaves Today, leaves the project, goes
   to Archive, project counts drop. One undo toast, as now.

### Drop lifecycle

```
pick up  -> lib/drag.ts resolves (bucket, projectId, parentId, before, after)
         -> optimistic local mutation in useBoard
         -> moveTask RPC
         -> server transaction: validate invariants, write ONE order column
         -> realtime broadcast -> board reconciles
```

## Execution plan

Six phases. TDD throughout — the repo already has db.test.ts (570),
drag.test.ts (677), TodoPage.test.tsx (771); new behaviour lands as failing
tests first.

**Phase 1 — schema + project CRUD** (lib/db.ts, lib/ids.ts, lib/db.test.ts)
Migrations 10-15, `mintProjectId`, project CRUD, the six invariants, the
FK-pragma check. Blocking; everything else waits.

**Phase 2 — moveTask rewrite** (lib/db.ts, lib/db.test.ts, lib/rollover.test.ts)
Stop nulling `parent_id`. Dual order columns. Project re-homing and snap-home.
Reverse the drag-children-along behaviour at db.ts:565. Prove rollover is
unaffected by re-running rollover.test.ts untouched. Depends on 1.

**Phase 3 — contract + server** (contract.ts, server.ts, server.test.ts)
Five new RPC methods, the moveTask/createTask/getBoard/TaskDto changes, trail
denormalization, backlog query returning ghosts. Depends on 2.

**Phase 4 — drag layer** (lib/drag.ts, lib/drag.test.ts)
Pure resolver; the whole drag matrix above becomes table-driven tests. Depends
on 3 (types only). Parallel with 5.

**Phase 5 — components** (ProjectGroup.tsx, ProjectHeader.tsx, TrailLine.tsx,
TaskRow.tsx, leaf.test.tsx) Presentational, driven by fixtures. Parallel with 4.

**Phase 6 — integration** (TodoPage.tsx, hooks/useBoard.ts, TodoPage.test.tsx,
docs/UX.md, docs/SPEC.md, README.md) Wire it together, update the three docs.
Depends on 4 + 5.

Order: 1 -> 2 -> 3 -> (4 || 5) -> 6.

### Risks

- **Ghost rows double the Backlog's visual weight** if a user schedules twenty
  things. Mitigation: ghosts are dimmed and compact; if it still reads badly, a
  per-project "hide scheduled" toggle is the follow-up, not part of this change.
- **The two order columns can drift** if a mutation writes the wrong one.
  Mitigation: a single `writeOrder(bucket)` helper is the only code path
  allowed to write either column, plus invariant test 5.
- **Migration 15's backfill runs once.** If it is wrong it is not re-runnable.
  Mitigation: test it against a fixture DB built from the pre-change schema
  before shipping.

### Rollback

Migrations are additive only. Reverting the code leaves two unused columns and
an unused table; the board renders exactly as it does today because
`project_id = NULL` is the loose-task path. No data is lost.

## Deviations accepted during Phases 1-3 (verified 2026-08-27)

1. **The Today query is now genuinely flat.** This document's Storage-plan
   section said it was "unchanged apart from ordering". That was wrong and
   contradicted invariant 4 plus the UX mockup: a subtask scheduled alone must
   appear in Today while its parent stays in the Backlog. The
   `parent_id IS NULL` filter is dropped; `buildTodayDto` forces
   `subtasks: []` on every Today row. **Accepted** — the invariant wins over
   the prose.

2. **`writeOrder` is keyed by column, not by bucket.** A bucket-keyed helper
   would clobber `sort_order` whenever `today_order` was written, which breaks
   ghost rows — they need both, independently, on the same row. Signature is
   `writeOrder(db, id, column, value, now)`. **Accepted**; the structural
   guarantee is stronger than specified, enforced by a source-scanning test.

3. **`PRAGMA foreign_keys` is ON**, set per-connection in `server.ts`.
   Migration 12 deliberately declares no `ON DELETE` clause, so the implicit
   behaviour would be `NO ACTION` (delete rejected), not a cascade.
   `deleteProject` therefore keeps its explicit release of tasks to
   `project_id = NULL` inside the transaction. **Accepted.**

4. **DEBT — `TaskDto.projectId` and `TaskDto.trail` are optional in TS,
   required in zod.** Relaxed only because off-limits test fixtures build
   `TaskDto` literals by hand. **Phase 6 must update those fixtures and remove
   the `?` from both fields.** The wire contract already requires them; this is
   a TS-only hole and it must not survive the change.

## Out of scope (deliberate)

- Nested projects / sub-projects. The list tab is already the outer level; a
  third container level is not earned yet.
- Project due dates, progress bars beyond the open count, per-project archive
  views.
- Drag-to-group (entry point 2 above).
- Cross-list project moves.
